# Задание 4. Логирование

## Анализ системы и C4-диаграмма в контексте логирования

### Какие логи нужно собирать

Система состоит из нескольких компонентов, каждый генерирует свои логи:

**Shop API (Java Spring Boot):**
- Изменение статуса заказа (INFO): время, идентификатор покупателя, номер заказа
- Ошибки при создании заказа (ERROR)
- API запросы от клиентов (INFO)

**CRM API (Java Spring Boot):**
- Подтверждение заказа менеджером (INFO)
- Изменение статуса заказа (INFO)
- Ошибки интеграции с Shop DB (ERROR)

**MES API (C#):**
- Расчет стоимости заказа (INFO): время начала/окончания, размер файла
- Назначение заказа на оператора (INFO)
- Ошибки при расчете (ERROR)
- Медленные запросы к БД (WARN)

**RabbitMQ:**
- Сообщения в dead-letter queue (ERROR)
- Задержки в обработке сообщений (WARN)

**Базы данных (Shop DB, MES DB):**
- Медленные запросы > 1 сек (WARN)
- Ошибки подключения (ERROR)
- Deadlocks (ERROR)

### Обновленная C4-диаграмма с компонентами логирования

**Новые компоненты (выделены на схеме):**
1. **Filebeat** - на каждом EC2 инстансе (собирает логи из файлов)
2. **Logstash** - централизованный (обрабатывает, фильтрует, маскирует данные)
3. **Elasticsearch** - хранилище логов (managed service Yandex Cloud)
4. **Kibana** - веб-интерфейс для поиска и дашбордов

**Новые связи:**
- Shop API/CRM API/MES API → Filebeat (запись логов в файлы)
- Filebeat → Logstash (отправка логов)
- Logstash → Elasticsearch (сохранение обработанных логов)
- Kibana → Elasticsearch (чтение логов для визуализации)
- Developers/Support → Kibana (поиск и анализ логов)

**Приоритет логирования:**

Команда не может реализовать логирование и трейсинг одновременно для всех систем. Приоритет:

1. **Первая очередь:** Shop API, CRM API - здесь теряются заказы, критично для бизнеса
2. **Вторая очередь:** MES API - проблемы с производительностью, но не теряются данные
3. **Третья очередь:** RabbitMQ, БД - инфраструктурные компоненты

**Почему такой приоритет:**
- Shop API и CRM API - точки входа заказов, здесь происходит потеря
- MES API - проблемы с производительностью менее критичны чем потеря заказов
- RabbitMQ и БД - можно мониторить стандартными средствами на первом этапе

## Мотивация

Сейчас заказы теряются и непонятно почему. Нет видимости что происходит в RabbitMQ, дашборд MES тормозит - не понятно где проблема, API-клиенты жалуются - нечем расследовать.

Логирование нужно чтобы:
- Отслеживать заказ через все системы
- Диагностировать проблемы производительности
- Анализировать ошибки интеграции
- Соблюдать SLA с B2B-клиентами

## Предлагаемое решение

### Архитектура

Используем ELK Stack:
- **Filebeat** - на каждом EC2, собирает логи
- **Logstash** - обрабатывает и фильтрует
- **Elasticsearch** - хранит (managed service Yandex Cloud)
- **Kibana** - поиск и дашборды

### Уровни логирования

- **ERROR** - критические ошибки, требуют немедленного внимания
- **WARN** - потенциальные проблемы (таймауты, повторные попытки)
- **INFO** - ключевые события (смена статуса заказа, API-запросы)
- **DEBUG** - детальная информация (только dev/release)

### Структура логов

Обязательные поля:
```json
{
  "timestamp": "2024-02-08T12:00:00Z",
  "level": "INFO",
  "service": "crm-backend",
  "trace_id": "abc123",
  "order_id": "12345",
  "message": "Order status changed to MANUFACTURING_APPROVED"
}
```

## Политика безопасности

**Запрещено логировать:** персональные данные (ФИО, адреса, телефоны), платёжные данные, пароли, токены, содержимое 3D-моделей.

**Маскирование:** Email → `user***@example.com`, Телефон → `+7***1234`, API-ключи → `sk_***xyz`

**Доступ:**
- Разработчики - полный к dev/release, read-only к prod (ERROR/WARN)
- DevOps - полный ко всем окружениям
- QA - read-only к release
- Бизнес - доступ запрещён

## Политика хранения

| Окружение | Уровень | Срок хранения | Индексация |
|-----------|---------|---------------|------------|
| Production | ERROR/WARN | 90 дней | Полная |
| Production | INFO | 30 дней | По order_id, trace_id |
| Production | DEBUG | Не хранится | - |
| Release | Все уровни | 14 дней | Полная |
| Dev | Все уровни | 7 дней | Минимальная |

Ротация индексов ежедневная. Максимальный размер лога 10 КБ, лимит 1000 записей/сек на сервис.

## Предотвращение превращения в систему анализа

Логирование - это не аналитика. Ограничения:
- Только поиск и фильтрация логов
- Простые дашборды (количество ошибок, топ-5 проблем)
- Запрет на сложные аналитические отчёты
- Отключение ML-функций Elasticsearch
- Aggregation-запросы не сложнее 2 уровней
- Максимальное время запроса 30 секунд

Интеграции:
- Алерты критических ошибок → Slack/Email
- Метрики из логов → Prometheus (только счётчики ошибок)
- Детальная аналитика → отдельная BI-система

## Выбор технологии

Обязательные требования: масштабируемость (10000 заказов/месяц), централизация, полнотекстовый поиск, managed service в Yandex Cloud, гибкая retention.

Дополнительно: structured logging (JSON), интеграция с Java/C#/Vue/React, готовые библиотеки, стоимость до 100 ГБ/месяц, обучение команды до 2 недель.
