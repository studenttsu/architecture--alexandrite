# Задание 1. Анализ, идентификация проблем и решений, планирование

## Выявленные проблемы

### Проблема 1: Потеря заказов и жалобы клиентов
Самая критичная проблема - теряются заказы. RabbitMQ настроен ненадежно, сообщения пропадают при сбоях и перезапусках. Нет механизма повторной обработки, нет мониторинга очередей. Плюс по одному инстансу каждого приложения - упадет сервис, и все сообщения в процессе обработки потеряются. Транзакционности между БД и очередью тоже нет.

### Проблема 2: Медленная загрузка дашборда операторов в MES
Дашборд тормозит из-за растущего объема данных (100 заказов в месяц). Запросы к БД неоптимальные - нет нужных индексов, есть N+1 проблема. Один инстанс БД обрабатывает и чтение, и запись - конкуренция за ресурсы. Кэширования нет, фильтры и пагинация, похоже, реализованы неэффективно.

### Проблема 3: Узкое место в расчете стоимости
Расчет стоимости тормозит всю обработку заказов. Все делается синхронно, MES не масштабируется, алгоритм расчета не оптимизирован.

### Проблема 4: Задержки релизов
Релизы постоянно задерживаются. Автотестов мало, один QA не справляется с объемом работы. Баги находятся поздно, на этапе release. Регрессионное тестирование не автоматизировано.

### Проблема 5: Отсутствие масштабируемости
Архитектура в принципе не рассчитана на горизонтальное масштабирование. Нет load balancer'а, один инстанс БД - это потолок по производительности.

## 3. Инициативы для устранения проблем

### Инициатива 1: Обеспечение надежности обработки сообщений
Главная проблема сейчас - теряются заказы из-за ненадежной работы с RabbitMQ. Нужно настроить persistent messages, чтобы сообщения не пропадали при перезапуске. Добавить Dead Letter Queues для обработки ошибок и retry механизм с exponential backoff. Обязательно внедрить idempotency keys, чтобы не было дублей заказов. Для критичных операций использовать outbox pattern - это гарантирует доставку.

Результат: заказы перестанут теряться, появится возможность отследить проблемные сообщения и переобработать их, клиенты перестанут жаловаться.

### Инициатива 2: Горизонтальное масштабирование приложений
Сейчас по одному инстансу каждого приложения - упадет один, все встанет. Нужен load balancer и минимум по 2 инстанса для каждого сервиса. Настроить auto-scaling по метрикам (CPU, память, глубина очередей). Проверить, что приложения stateless, если нет - использовать Redis для shared sessions.

Результат: не будет единой точки отказа, система сможет обрабатывать растущую нагрузку, общая отказоустойчивость вырастет.

### Инициатива 3: Оптимизация производительности MES
Дашборд операторов тормозит из-за растущего объема данных. Добавить read replicas для БД MES, создать индексы на статус заказа и дату создания. Внедрить кэширование через Redis. Оптимизировать SQL-запросы - убрать N+1 проблему, использовать JOIN. Для сложных агрегаций можно попробовать материализованные представления.

Результат: дашборд будет грузиться быстро, нагрузка на основную БД снизится, операторы будут довольны.

### Инициатива 4: Асинхронная обработка расчета стоимости
Расчет стоимости сейчас тормозит всю обработку заказов. Вынести его в отдельный worker service, использовать очередь задач (можно тот же RabbitMQ). Масштабировать воркеры независимо от MES. Добавить приоритеты - например, B2C обрабатывать быстрее. Сделать уведомления о готовности расчета через webhook или websocket.

Результат: можно будет обрабатывать больше запросов параллельно, гибко масштабировать вычислительные ресурсы, API будет отвечать быстрее.

### Инициатива 5: Мониторинг и алертинг
Сейчас не видно, что происходит в системе. Поднять Prometheus + Grafana (или Yandex Monitoring). Собирать метрики: latency, throughput, error rate, queue depth. Добавить distributed tracing (Jaeger или Zipkin), чтобы отслеживать путь заказа. Настроить алерты на критичные метрики. Health checks для всех сервисов.

Результат: проблемы будут находиться раньше, можно будет отследить весь путь заказа, решать проблемы до того, как клиенты начнут жаловаться.

### Инициатива 6: Автоматизация тестирования
Один QA не справляется, релизы задерживаются. Написать E2E тесты для критичных сценариев, integration tests для RabbitMQ, contract testing для API. Встроить автотесты в CI/CD, запускать на каждом PR и перед релизом.

Результат: релизы пойдут быстрее, регрессии будут находиться раньше, QA разгрузится.

### Инициатива 7: Database scaling и оптимизация
Настроить read replicas для всех БД. Читать с реплик, писать в master. Добавить connection pooling. Найти медленные запросы и оптимизировать. Для старых заказов можно партиционировать таблицы по дате.

Результат: master БД разгрузится, чтение станет быстрее, система будет готова к росту.

### Инициатива 8: Улучшение процесса разработки
Внедрить feature flags для постепенного раскатывания фич. Автодеплой в dev после merge. Smoke tests после деплоя. Code review checklist с акцентом на производительность и надежность. Регулярные ретроспективы.

Результат: меньше рисков при релизах, можно быстро откатить проблемные изменения, качество кода вырастет.

## 4. Приоритизация инициатив

При выборе приоритетов смотрел на несколько вещей: насколько критична проблема для бизнеса, как срочно нужно решение, сколько времени займет реализация и есть ли зависимости от других задач.

### Высокий приоритет - делать в первую очередь:

**1. Надежность обработки сообщений**  
Это самое важное. Теряем заказы и клиентов - критично для бизнеса. Плюс реализуется быстро, за 2-3 недели. Нужен один Java-разработчик, один C#-разработчик и DevOps. Риски низкие, это стандартные практики для RabbitMQ.

**2. Мониторинг и алертинг**  
Без этого не увидим, работают ли остальные инициативы и где проблемы. Сделать можно за 2 недели силами DevOps и тимлида. Готовые решения есть, риски минимальные.

**3. Горизонтальное масштабирование**  
Убирает единую точку отказа и готовит к росту. Займет 3-4 недели. Нужен DevOps плюс по одному разработчику от каждого стека, чтобы проверить, что приложения stateless. Риски средние - надо убедиться, что архитектура позволяет.

### Средний приоритет - делать во вторую очередь:

**4. Оптимизация производительности MES**  
Дашборд тормозит, операторы недовольны. Но это не так критично, как потеря заказов. Реализация 2-3 недели, один C#-разработчик и DevOps для Redis. Риски низкие.

**5. Асинхронная обработка расчета стоимости**  
Снимает узкое место, особенно для B2B. Но требует рефакторинга MES, поэтому 4-5 недель и 1-2 C#-разработчика. Риски средние.

**6. Database scaling**  
Дополняет оптимизацию MES, готовит к росту. 2-3 недели, DevOps плюс разработчики для оптимизации запросов. Read replicas - низкие риски, партиционирование - средние.

### Низкий приоритет - долгосрочные улучшения:

**7. Автоматизация тестирования**  
Важно для стабильности, но текущие критичные проблемы не решает. Делать итеративно, 6-8 недель. QA плюс по разработчику от каждого стека. Риски низкие.

**8. Улучшение процесса разработки**  
Процессные вещи, эффект накопительный. Делать постоянно всей командой. Риски низкие.

## 5. Ответы на вопросы

### Какой вы видите целевую архитектуру через полгода?

Через полгода архитектура должна стать гораздо более устойчивой и готовой к росту. 

Во-первых, все приложения нужно запускать минимум в двух экземплярах с балансировщиком нагрузки. Сейчас у нас один инстанс каждого сервиса - это очень рискованно. Плюс настроить автомасштабирование, чтобы система сама подстраивалась под нагрузку.

С базами данных похожая история - добавить read replicas, чтобы разгрузить основную БД. Запросы на чтение пойдут на реплики, а запись останется на мастере. Для часто используемых данных поднять Redis - и для кэша, и для хранения сессий.

RabbitMQ нужно настроить как следует: persistent messages, dead letter queues, retry механизм. Сейчас сообщения теряются, а это недопустимо. Для критичных операций внедрить outbox pattern.

Расчет стоимости лучше вынести в отдельный сервис, который можно масштабировать независимо от MES. Сейчас это узкое место, особенно для B2B заказов.

Обязательно нужен нормальный мониторинг - Prometheus с Grafana или что-то подобное. Чтобы видеть, что происходит в системе, где тормозит, где растет нагрузка. Distributed tracing тоже пригодится, чтобы отслеживать путь заказа через все сервисы.

Ну и автотесты, конечно. E2E тесты для основных сценариев, интеграционные тесты для взаимодействия через очереди. Запускать их автоматически перед каждым релизом.

В итоге получим систему без единых точек отказа, которая выдержит рост в 3-5 раз и позволит быстро находить и исправлять проблемы.

### Если бы у вас была возможность выполнить только три пункта из списка инициатив в ближайшие полгода, что бы вы выбрали и почему?

Если выбирать только три вещи, то вот что:

**Первое - надежность обработки сообщений.** Это самое критичное. Мы теряем заказы, клиенты жалуются, уже потеряли несколько B2B контрактов. Нужно срочно настроить RabbitMQ правильно - persistent messages, DLQ, retry. Плюс добавить idempotency, чтобы не было дублей. Это можно сделать за 2-3 недели, а эффект будет сразу.

**Второе - горизонтальное масштабирование.** Один инстанс каждого приложения - это бомба замедленного действия. Упадет сервис - все встанет. Нужен load balancer и минимум по два инстанса. Это даст и отказоустойчивость, и возможность расти дальше. Логично делать после первого пункта.

**Третье - асинхронный расчет стоимости.** Сейчас это узкое место, особенно для B2B. Вынести расчеты в отдельный сервис с очередью задач, масштабировать воркеры по нагрузке. Можно добавить приоритеты - например, B2C обрабатывать быстрее. Это снимет проблему с производительностью и даст гибкость.

Эти три вещи решают самые болезненные проблемы и создают фундамент для дальнейшего развития. Остальное можно делать потом, когда система станет стабильнее.
