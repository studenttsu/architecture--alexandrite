# Задание 2. Мониторинг

### Мотивация

Сейчас у компании серьезные проблемы из-за отсутствия visibility в системе:
- Теряются заказы - непонятно где (RabbitMQ, БД, интеграции)
- Заказы выполняются месяцами вместо обещанных 3 недель - нет данных по узким местам
- Дашборд MES тормозит - не видно производительности БД и медленных запросов
- B2B клиенты жалуются - нет метрик API (RPS, latency, error rate)
- Команда узнает о проблемах от клиентов, а не проактивно

Что даст мониторинг:
- Улучшить MTTD (среднее время обнаружения) благодаря алертам
- Улучшить MTTR (среднее время восстановления) благодаря быстрой диагностике
- Данные для планирования масштабирования и capacity planning
- Возможность гарантировать SLA для B2B клиентов
- Понимание где нужны ресурсы, а где избыток

### Выбор подхода к мониторингу

Для бэкенда (Shop API, CRM API, MES API) и брокера (RabbitMQ) подходят "USE" и "Четыре золотых сигнала от Google" - они покажут как серверы справляются с нагрузкой и трафиком.

Для взаимодействия с пользователями подходит "RED" - он покажет частоту запросов, ошибок и время выполнения.

Выбираю **"Четыре золотых сигнала"** (Latency, Traffic, Errors, Saturation), потому что:
- Комбинирует преимущества RED и USE
- **Latency** - критична для UX (медленный дашборд MES, долгий расчет стоимости)
- **Traffic** - нужен для планирования масштабирования (рост 100 заказов/месяц)
- **Errors** - прямо связаны с потерей заказов и жалобами клиентов
- **Saturation** - помогает найти узкие места (RabbitMQ, БД, CPU/память)

Адаптация для компонентов:
- **API/веб-приложения:** latency (время ответа), traffic (RPS), errors (HTTP 4xx/5xx), saturation (CPU/память/соединения)
- **RabbitMQ:** latency (время обработки), traffic (сообщений/сек), errors (DLQ), saturation (глубина очередей/память)
- **БД:** latency (время запросов), traffic (запросов/сек), errors (failed connections/deadlocks), saturation (CPU/память/disk I/O)

### Метрики

#### RabbitMQ
- **Number of dead-letter-exchange letters**
  - Показывает сообщения, которые не удалось обработать - прямо связано с потерей заказов
  - Ярлык: `rabbitmq-dlq`
  - Алерт: Warning > 0, Critical > 10 за 5 минут
  
- **Number of messages in flight**
  - Сообщения в процессе обработки, помогает найти зависшие
  - Ярлык: `rabbitmq-in-flight`
  - Алерт: Warning > 5 минут, Critical > 15 минут
  
- **Queue depth**
  - Количество необработанных сообщений, индикатор проблем с производительностью consumers
  - Ярлык: `rabbitmq-queue-depth`
  - Алерт: Warning > 1000, Critical > 5000
  
- **CPU %**
  - При высокой загрузке возможна потеря сообщений
  - Ярлык: `rabbitmq-cpu-usage`
  - Алерт: Warning > 70%, Critical > 90%
  
- **Memory Utilisation**
  - При нехватке памяти возможна потеря сообщений
  - Ярлык: `rabbitmq-mem-usage`
  - Алерт: Warning > 80%, Critical > 95%

#### Shop API / CRM API / MES API
- **Number of requests (RPS)**
  - Нагрузка на сервис, планирование масштабирования, выявление аномалий (DDoS)
  - Ярлык: `$serviceName-rps`
  - Алерт: Warning +50% за 10 мин, Critical +200% за 5 мин
  
- **CPU %**
  - Загрузка процессора, индикатор масштабирования
  - Ярлык: `$serviceName-cpu-usage`
  - Алерт: Warning > 70% (5 мин), Critical > 90% (2 мин)
  
- **CPU Load Average**
  - Загрузка CPU на задачу
  - Ярлык: `$serviceName-cpu-load-average`
  - Алерт: Warning > 0.7, Critical > 1.0
  
- **Memory Utilisation**
  - Использование памяти, выявление утечек
  - Ярлык: `$serviceName-mem-usage`
  - Алерт: Warning > 80%, Critical > 95%
  
- **SWAP usage**
  - Использование файла подкачки
  - Ярлык: `$serviceName-swap-usage`
  - Алерт: Warning > 10%, Critical > 50%
  
- **Response time (latency)**
  - Время ответа, влияет на UX и B2B SLA
  - Ярлык: `$serviceName-response-latency`
  - Алерт: Warning p95 > 1 сек (обычные) / > 5 мин (расчет), Critical p95 > 3 сек / > 15 мин
  
- **Number of HTTP 200**
  - Количество успешных ответов
  - Ярлык: `$serviceName-response-success`
  
- **% of HTTP 200**
  - Процент успешных ответов
  - Ярлык: `$serviceName-response-success-pct`
  
- **Number of HTTP 500**
  - Количество ошибок
  - Ярлык: `$serviceName-response-error`
  
- **% of HTTP 500**
  - Процент ошибок, основа для SLA
  - Ярлык: `$serviceName-response-error-pct`
  - Алерт: Warning > 1%, Critical > 5%
  
- **Kb transferred (received)**
  - Исходящий трафик. Для анализа и контроля бюджета на защиту от DDOS
  - Ярлык: `$serviceName-traffic-received`
  
- **Kb provided (sent)**
  - Входящий трафик. Для анализа и контроля бюджета на защиту от DDOS
  - Ярлык: `$serviceName-traffic-sent`

#### БД (Shop DB / MES DB)
- **CPU %**
  - Загрузка CPU
  - Ярлык: `$serviceName-db-cpu-usage`
  - Алерт: Warning > 70%, Critical > 90%
  
- **Memory Utilisation**
  - Загрузка памяти, критично для производительности БД
  - Ярлык: `$serviceName-db-mem-usage`
  - Алерт: Warning > 85%, Critical > 95%
  
- **SWAP usage**
  - Использование файла подкачки
  - Ярлык: `$serviceName-db-swap-usage`
  - Алерт: Warning > 10%, Critical > 50%
  
- **Disk Utilisation**
  - Занятое дисковое пространство. Для контроля и расширения при необходимости
  - Ярлык: `$serviceName-db-disk-usage`
  - Алерт: Warning > 80%, Critical > 95%
  
- **Number of connections**
  - Нагрузка на БД, проблемы с connection pooling
  - Ярлык: `$serviceName-db-connections`
  - Алерт: Warning > 80% от max, Critical > 95% от max
  
- **Query latency (slow queries)**
  - Медленные запросы, критично для дашборда MES
  - Ярлык: `$serviceName-db-query-latency`
  - Алерт: Warning > 1 сек, Critical > 5 сек

#### Дополнительные метрики
- **Order processing time (end-to-end)**
  - Время от создания до отправки, связано с жалобами на просроченные заказы
  - Ярлык: `order-processing-time`
  - Алерт: Warning > 3 недели, Critical > 6 недель
  
- **S3 storage size**
  - Планирование расходов, выявление аномального роста
  - Ярлык: `s3-storage-size`
  - Алерт: Warning рост > 50% за неделю

### Показатели насыщенности

Насыщенность - опережающий индикатор проблем. Показывает насколько ресурс близок к пределу. Позволяет масштабироваться до того, как пользователи почувствуют деградацию.

Пример: CPU 80% - нормально, если нет очереди. Но CPU 80% + queue length 100 - это насыщенность, пора масштабироваться.

#### Пороговые значения и алерты

- **CPU Usage > 80%**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: подготовить план масштабирования

- **CPU Load Average > 1.0 (на ядро)**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: немедленно добавить инстансы или увеличить CPU

- **Memory Usage > 80%**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: оптимизировать память или увеличить RAM

- **Swap Usage > 50%**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: немедленно увеличить RAM (swap в 1000x медленнее)

- **DB Disk Size > 80%**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: расширить диск или архивировать старые данные

- **RabbitMQ Queue Depth > 1000**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: добавить consumers, проверить зависшие обработчики

- **DB Connection Pool > 80%**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: оптимизировать запросы, увеличить пул, добавить read replica

- **Disk I/O Busy > 80%**
  - Уведомление в Telegram, Email
  - Создание задачи в Jira
  - Действие: увеличить IOPS или перейти на SSD

**Стратегия:** Масштабироваться при 60-80% (желтая зона), не ждать 100%. Анализировать тренды, прогнозировать когда ресурсы достигнут предела, планировать заранее.
