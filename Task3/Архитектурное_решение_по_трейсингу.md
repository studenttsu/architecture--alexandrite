# Задание 3. Трейсинг

## Мотивация

Сейчас команда не может ответить на простой вопрос "Где мой заказ?". Клиенты звонят, менеджеры не знают что ответить - заказ где-то застрял. Когда заказ теряется, команда тратит часы на поиск: смотрят логи каждого сервиса, базы данных, очереди RabbitMQ.

Заказы выполняются месяцами, но непонятно где именно задержка. Заказ проходит через 3 приложения, 3 базы данных, RabbitMQ - логи разрознены, нет единого идентификатора.

Трейсинг даст:
- Быструю диагностику - от часов до минут
- Возможность за секунды найти заказ и увидеть на каком этапе он находится
- Визуализацию времени на каждом этапе (расчет 25 минут, ожидание в очереди 3 дня)
- Единый trace ID через все компоненты
- Алерты на аномально долгие операции
- Возможность гарантировать SLA для B2B клиентов

### Данные для трейсинга

**Обязательные:** Trace ID, Span ID, Parent Span ID, Timestamp, Service name, Operation name, Status, Duration

**Бизнес-контекст:** order_id, customer_id, order_status, order_type (B2C/B2B), api_key, file_size, price

**Технический контекст:** http.method/url/status_code, db.statement, messaging.destination, error.message/stack

## Предлагаемое решение

### Выбор технологии

Рассмотрели три варианта:
- **Jaeger** - open source, хорошая визуализация, совместим с OpenTelemetry, но требует инфраструктуры
- **Zipkin** - open source, простой, но менее функциональный
- **AWS X-Ray / Yandex Cloud Tracing** - managed service, но vendor lock-in и дороже

**Выбор: Jaeger + OpenTelemetry**

Jaeger - индустриальный стандарт, отличная визуализация (waterfall диаграммы), активное сообщество. OpenTelemetry - vendor-neutral стандарт, единый SDK для метрик/логов/трейсов, автоматическая инструментация, гибкость (можно менять backend без изменения кода).

### Архитектура

**Компоненты:**
1. **OpenTelemetry SDK** - в каждом приложении (автоинструментация HTTP/БД/RabbitMQ, создание trace context, отправка spans)
2. **Jaeger Agent** - на каждом EC2 (прием spans, батчинг, отправка в Collector)
3. **Jaeger Collector** - централизованный (прием от агентов, валидация, запись в хранилище)
4. **Jaeger Storage** - Elasticsearch (хранение 30 дней, индексация, быстрый поиск)
5. **Jaeger Query & UI** - веб-интерфейс (поиск трейсов, waterfall диаграммы, фильтрация по тегам)

### Инструментация приложений

**Shop API (Java Spring Boot):**
- Автоматическая инструментация через OpenTelemetry Java Agent
- JVM параметры: `-javaagent:opentelemetry-javaagent.jar -Dotel.service.name=shop-api`
- Добавление бизнес-контекста: `span.setAttribute("order.id", orderId)`, `span.setAttribute("customer.id", customerId)`

**MES API (C#):**
- Установить пакеты: OpenTelemetry, OpenTelemetry.Exporter.Jaeger, OpenTelemetry.Instrumentation.AspNetCore
- Настроить в Startup.cs: AddOpenTelemetryTracing с AspNetCore/Http/SqlClient instrumentation
- Добавление контекста: `activity?.SetTag("order.id", orderId)`, `activity?.SetTag("price", price)`

**RabbitMQ интеграция:**
- Producer: inject trace context в headers сообщения через TextMapPropagator
- Consumer: extract trace context из headers, создать span с parent context
- Передача trace ID через все сообщения для связности трейсов

### Изменения в архитектуре

**Новые компоненты:** OpenTelemetry SDK (в каждом приложении), Jaeger Agent (на каждом EC2), Jaeger Collector (централизованный), Elasticsearch (хранилище), Jaeger Query & UI (веб-интерфейс)

**Новые связи:** Приложения → Jaeger Agent → Jaeger Collector → Elasticsearch ← Jaeger Query ← Developers/Support

**Trace context propagation:** HTTP (через headers traceparent/tracestate), RabbitMQ (через message headers), БД (автоматически через OpenTelemetry)

## Компромиссы

**Когда трейсинг НЕ нужен:**
- Простая система (один монолит, синхронные операции) - у нас распределенная из 3 приложений
- Миллионы простых запросов/сек - у нас ~100 заказов/месяц, каждый ценный
- Нет проблем с производительностью - у нас серьезные проблемы с потерей заказов

**Принимаемые компромиссы:**

1. **Performance overhead ~1-5%** - приемлемо, система не под высокой нагрузкой. Митигация: sampling (100% заказов, 10% health checks)

2. **Сложность системы** - добавляется компонент в инфраструктуру, но упрощает отладку. Митигация: managed Elasticsearch от Yandex Cloud

3. **Конфиденциальность** - трейсы могут содержать чувствительные данные, но хранятся внутри инфраструктуры. Митигация: не логировать PII (имена, email, телефоны), только ID

## Аспекты безопасности

**Риски:**
1. **Утечка чувствительных данных** - трейсы могут содержать персональные данные, API ключи, токены (нарушение GDPR)
2. **Несанкционированный доступ** - если Jaeger UI без аутентификации, утечка бизнес-информации
3. **Инъекция вредоносных данных** - атака через trace headers (SQL injection, XSS)

### Меры по предотвращению

**1. Фильтрация чувствительных данных**
- Не логировать: пароли, токены, API ключи, номера карт, персональные данные (имена, email, телефоны), содержимое файлов
- Логировать только ID: `customer.id` вместо `customer.email`, маскировать URL параметры
- Использовать OpenTelemetry Span Processors для автоматической фильтрации чувствительных атрибутов

**2. Аутентификация и авторизация**
- Jaeger UI за reverse proxy (Nginx) с базовой аутентификацией или OAuth 2.0
- Интеграция с корпоративным SSO через Yandex Cloud IAM
- RBAC и аудит доступа к трейсам

**3. Шифрование**
- В транзите: TLS для всех соединений (приложения → Agent → Collector)
- В хранилище: encryption at rest для Elasticsearch (Yandex Managed Elasticsearch)

**4. Сетевая изоляция**
- Jaeger Collector, Elasticsearch - только в приватной подсети
- Jaeger UI - за VPN или bastion host
- Firewall: разрешить только приложениям → Agent → Collector, запретить внешний доступ

**5. Валидация входных данных**
- Валидация trace context (trace-id, span-id) для защиты от инъекций

**6. Retention и GDPR**
- Автоматическое удаление трейсов старше 30 дней (Elasticsearch ILM)
- Возможность удалить трейсы конкретного клиента по запросу
- Документировать хранимые данные

**7. Аудит**
- Логировать доступ к Jaeger UI
- Алерты на подозрительную активность (множественные неудачные попытки, необычные IP, массовая выгрузка)
